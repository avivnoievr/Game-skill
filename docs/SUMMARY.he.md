# Game Studio 3D — מה יש בסקיל ואיך עובדים איתו

גרסה **1.1.0**, 10 באוקטובר 2026. הריפו: [avivnoievr/Game-skill](https://github.com/avivnoievr/Game-skill).
זו הרחבה של עבודת Claude שהועברה ב־commit `8128088`. התוצר הוא סקיל ופלאגין ל־Claude Code,
עם הוראות עבודה, סוכנים, מקורות מורשים וכלים שרצים בפועל. המשחק עצמו אינו נמצא בריפו הזה.

הסקיל מיועד למודל חזק. הליבה לא מלמדת מחדש תכנות או Blender: היא מוסיפה החלטות ייצור,
גבולות בעלות, סדר עבודה וראיות שאסור לדלג עליהן. הספרייה רחבה, אבל נטענת לפי צורך.
אין כאן הבטחה שפרומפט יהפוך כל מודל למעצב מקצועי.

## הזרימה מהפרומפט ועד הייצור

1. המנהל טוען את הסקיל, קורא הוראות פרויקט וזיכרון, מזהה מה קיים ומכין brief קצר.
2. כשזה משחק חדש, כשאין תוכנית שימושית או כשכוונת המשחק השתנתה, מתחילים **שני סוכנים במקביל**.
3. `genre-art-researcher` בודק ז׳אנר, טון, חוויית שחקן, מצלמה ורפרנסים; משווה כיוונים וממליץ.
4. `production-planner` ממפה לולאת משחק, התקדמות, מערכות ותלויות; מכין טיוטת מקטע מייצג ואבני דרך.
5. המנהל מחבר את שני הדוחות ל־`design/plan.md`, פותר החלטות תלויות עיצוב ומגדיר בעלים, תקציבים ובדיקות יציאה.
6. רק אז מתחילים ייצור: greybox → נכסים ואנימציה מייצגים → שילוב → ביקורת → הרחבה.

הטיוטה המקבילית אינה מחליפה את התוכנית הסופית. המחקר והתוכנית נשמרים ומשמשים גם בסשנים
הבאים; לא מריצים שני חוקרים מחדש בשביל כל תיקון קטן. בדיקת web מלאה נחסמת כשדוח המחקר
או התוכנית הסופית חסרים. קיום קובץ לבדו אינו הוכחה שהתוכנית טובה — המנהל עדיין בודק את תוכנה.

בדוגמה שלך, ״סימולטור״ מתאר מכניקות ולא מחייב גרפיקה ריאליסטית. משחק גדילה וסיפור אבסורדי
יכול להתאים לצורות מוגזמות ותנועה קומית. זו השערה שמנמקים ובודקים, לא כלל ״מצחיק = low-poly״.
התכנון צריך להתייחס לשינויי פרופורציות, יכולות, rig, אנימציה, collision ומצלמה בכל גיל.

הפעלנו את שני התפקידים על הדוגמה כבדיקת הזרימה. החוקר קרא ארבעה מקורות ראשוניים של
יוצרים/מוציאים לאור; הוא לא טען שצפה בווידאו. התכנון זיהה את סיכוני הגדילה והציע מקטע קטן.
המנהל שילב את הדוחות בתוכנית הדגמה. זו אינה תוכנית מאושרת למשחק האמיתי שלך:
[מחקר](evidence/startup-research.md), [טיוטה](evidence/startup-plan-draft.md), [שילוב](evidence/startup-plan.md).

## ששת הסוכנים

| סוכן | אחריות | תוצר |
|---|---|---|
| `genre-art-researcher` | מחקר כוונת המשחק וכיווני עיצוב ותנועה | `design/research.md`, עם מקורות ומגבלות |
| `production-planner` | תלויות, מערכות, היקף וסדר ביצוע | `design/plan-draft.md`; המנהל אחראי לתוכנית הסופית |
| `asset-builder` | נכס עצמאי: מקור → מודל → ייצוא → בדיקות → תמונות | מקור ניתן לעריכה, runtime asset וראיות |
| `animator` | rig, clips, תזמון, מגע והעברת נתונים למנוע | מקור אנימציה, רצועות תנוחות ובדיקות תנועה |
| `art-critic` | ביקורת חזותית עצמאית, ללא עריכת התוצר | `ART-GATE: PASS/FAIL` עם ראיות לכל פגם |
| `playtest-qa` | קלט, פיצ׳רים, שגיאות, תקציבים ותשתית | `QA-GATE: PASS/FAIL` על גרסה מסוימת |

המנהל נשאר אחראי לשיחה, כיוון, קוד משותף ושילוב. במהלך הפקת משחק יש עד שלושה סוכנים
במקביל, ללא קינון; בסצנת Blender חיה יש כותב אחד. נכסים עצמאיים יכולים להיבנות בתהליכים
נפרדים. משתמשים ב־`model: inherit`; הגדרות הסקיל אינן מחליפות את המודל שנבחר בלקוח.
המחקר והבדיקות בהמשך הזה בוצעו בסוכני Codex, לא בהרצה של Opus.

## אילו סקילים שולבו בפועל

אלה חמישה רכיבים משלושה ריפואים, שהועתקו כקובצי עזר מורשים. הם אינם חמישה פלאגינים
שצריך להתקין. קובצי הכניסה המקוריים נקראים `UPSTREAM-SKILL.md`, כדי שלא יופעלו כסוכנים עצמאיים.

| רכיב | מה נלקח | שימוש |
|---|---|---|
| `threejs-aaa-graphics-builder` | ליבה, technical-art, כרטיס ביקורת ותמונות המקור | שפה חומרית, בדיקת סצנה ותקציבי רינדור |
| `threejs-game-ui-designer` | ליבה ו־UI patterns | HUD שמשרת מצבי משחק, היררכיה ומוטיבים מהעולם |
| `game-feel` | קובץ עזר למשוב ותנועה | טבלת אירוע→תגובה, תזמון ותנועה דטרמיניסטית |
| Anthropic `frontend-design` | ליבה ורישיון מקומי | החלטות ספציפיות לנושא, ריסון וביקורת עיצוב; לא תחליף למלאכת 3D |
| `game-ui-ux` | ליבה ו־layout-and-flow | focus, חלונות, בעלות קלט, safe areas ונגישות |

המקורות המדויקים:

- threejs-game-skills, MIT: `8286774b22a2566bf894dbc825825c16921866af`.
- anthropics/skills, Apache-2.0: `dbd4588f9e1033efb41dad4bef2f7947c8993d44`.
- awesome-gamedev-agent-skills, Apache-2.0 ו־NOTICE: `0a70cfc64672d512c5b5b6006b5dcb5cf90dbdbd`.

18 קובצי מקור אומתו מול Git blobs ו־SHA-256. הרישיונות נשמרים לצד הרכיבים, וההודעות המלאות
נמצאות בתוך הסקיל גם בהתקנה מועתקת. הפרטים ב־
[THIRD_PARTY_NOTICES](../plugins/game-studio/skills/game-studio/THIRD_PARTY_NOTICES.md)
וב־`vendor/sources.json`. מקורות נוספים השפיעו על העבודה בלי שהועתקו כסיקילים;
[CREDITS](CREDITS.md) מבדיל בין העתקה לבין מחקר ורעיונות.

לא אימצנו הוראות upstream ליצור נכסים בתשלום רק כי קיים API key, לקרוא לכלים שאינם
מותקנים, או להשתמש בסגנון צפוף/זוהר כמדד לאיכות. גם ציוני תמונות הדוגמה של המקור אינם
רף האיכות שלנו. `references/design-loading.md` נפתח בתחילת העבודה ובוחר חומר לכל שלב,
כדי שהמקורות לא ייצרו הוראות סותרות או העמסת הקשר.

## מודלים, כלים ומקור ניתן לעריכה

לפני בנייה מגדירים חלקים סמנטיים, pivots, joints, sockets, collision, מידות ותקציב.
גלגלים, דלתות או rotor שצריכים לנוע נשארים נפרדים. אפשר לאחד חלקים סטטיים באותו גוף קשיח
בעותק הייצוא; שומרים מקור/build recipe שמאפשר עריכה. Mesh מאוחד עם פרטים מצוירים אינו
תחליף למכניקה ולחלקים שהמשחק צריך לשלוט בהם.

| כלי/קובץ | מה הוא עושה |
|---|---|
| `find_blender.sh` | מוצא ובודק Blender קיים; מאפשר override מפורש; לא מתקין עותק נוסף |
| `gs_build.py` | צורות ממקטעים/פרופילים, bevel/recess, חומרים, חלקים, joints/sockets, atlas וייצוא |
| `templates/build.py` | התחלה לבנייה הניתנת לשחזור; הקובייה שבתבנית מסומנת blockout |
| `inspect_model.py` | תקציבים, מידות, מבנה, חלקים נדרשים, pivots, sockets, קבוצות קשיחות ו־collision נפרד |
| `render_views.py` | מבטים קבועים, silhouette, חומריות, קנה מידה ותצוגת חלקים מפורקת |
| `clip_report.py` | מדדי אנימציה כולל קפיצת סיבוב שבדיקת מיקום בלבד מפספסת |
| `capture.mjs` | דפדפן אמיתי: תמונות, קלט, מצב, שגיאות, מדדים ו־reloads; מצב gate דורש QA hook |
| `check_gltf.mjs` | Khronos validator כשמותקן, ובדיקות תקציב שלא מעבירות מדד חסר |
| `verify.sh` | כניסה לבדיקות web; בדיקות או קובצי תכנון חסרים חוסמים מעבר |

נוספו הוראות עבודה ל־Blender חי, בחירת כלים, טקסטורות, אודיו ותכנון שלבים, ומתכונים לרכב,
נכס מפרקי, kit מודולרי, דמות ממקור מורשה וסביבה. אלה חוזי עבודה ובדיקות, לא מדריך API למתחילים.
MCP הוא דרך גישה לכלי; הוא לא מקנה מעצמו חוש עיצוב. בחיבור חי בודקים הרשאות/גרסה ובעלות,
ושומרים על הסצנה. בדיקות שמאפסות סצנה רצות בתהליך נפרד. חיבור blocked לא מצדיק ביטול safe mode.

## בקרת איכות ותיקונים שנבדקו

עברו **57 בדיקות נסיגה**, ועוד בדיקת שליטה ב־Godot עם שמונה תנאים שעברו.
הפירוט והפקודות הניתנות לשחזור נמצאים ב־[VALIDATION](VALIDATION.md).

- תיקנו PASS שקרי בפרויקט ללא בדיקות, hooks שמחזירים שגיאה, מדדים חסרים ותקציב אפס.
- חריגה מתקציב משולשים מפורש נכשלת גם אם היא קטנה. אין החלפת נתון חסר באפס.
- תיקנו recess שיצר קוצים בגג הרכב ו־atlas שאיבד חומרים זוהרים בייצוא.
- תיקנו פער ממשי בין צמיג וחישוק באמצעות גאומטריה, בלי לשנות את סף הבדיקה.
- הוספנו בדיקות בעלות ומשאבים משותפים, שמירת context ותצוגה מפורקת הפיכה.
- תיקנו בדיקת אנימציה שהעבירה קפיצת סיבוב של 90 מעלות כשה־bone head נשאר באותו מקום.
- ההתקנה שומרת התאמות קודמות ומעבירה גם את הודעות המקור והרישוי.

רכב הבדיקה עבר בדיקה קפדנית ללא כישלונות או אזהרות: 10,098 משולשים מול תקציב fixture של
12,000, חמישה render meshes, ארבעה גלגלים נפרדים, שלושה חומרים ושתי תמונות atlas.
הוא נשאר דוגמה פשוטה — לא רכב hero מפורט.

סוכן עצמאי בנה מאוורר אחר לפי הסקיל: 2,344 משולשים, שלושה חלקים ושני חומרים. ב־Godot
הרוטור מסתובב והבסיס, המגן וה־socket נשארים במקום; מקור Blender נפתח מחדש. זה מוכיח זרימה
ושליטה בנכס, לא עיצוב מקצועי של משחק שלם. תמונות לפני/אחרי, חומריות וחלקים נפתחו ונבדקו.

## מה עדיין לא הוכח

הבדיקות כאן השתמשו ב־Blender 4.3.2 וב־Godot 4.6.3. לא נבדק חיבור GUI/MCP למחשב הפרטי שלך,
Unity, PowerShell בפועל, שירות יצירה בתשלום או ביצועי GPU אמיתי. מנועי Godot/Unity כוללים
מתכוני capture חלקיים, לא מערכת QA מלאה לכל משחק. Unreal אינו כולל adapter בדוק.
Khronos validator אינו מותקן בסביבה הזו; ה־pilot לא מוצג כעובר את הבדיקה הזו.

במחקר שהועבר יש הערות מבוססות כתוביות ל־15 סרטוני YouTube. בהמשך הזה נעשה שימוש במקורות
כתובים ראשוניים ובמטא־דאטה; לא צפינו ישירות בסרטונים. גישה ציבורית ל־Instagram נכשלה,
ולא הומצאו ממצאים מפוסטים. רישיונות ומחקר אינם הוכחה לטעם או לעלייה באיכות המשחק שלך.
השלב המשמעותי הבא הוא יישום הסקיל על הפרויקט האמיתי והשוואת תוצאה מול רפרנסים ומצלמת משחק.

## התקנה והתחלה

הוראות התקנה ב־[README](../README.md). בסשן ענן שמתקין קבצים בפרויקט:

```bash
git clone https://github.com/avivnoievr/Game-skill
bash Game-skill/install.sh /path/to/your-game
```

אחרי ההתקנה פותחים סשן חדש בריפו של המשחק ומדביקים את הפרומפט העברי ב־[PROMPT.md](../PROMPT.md).
שם מופיעים במפורש שני סוכני הפתיחה, שילוב המחקר בתוכנית, שמירת חלקים ובקרת האיכות.
בהתקנת קבצים מפעילים `/game-studio`; בפלאגין `/game-studio:game-studio`.
אין צורך להתקין את מקורות העיצוב בנפרד. לשלב הבא עם Claude קוראים גם את [HANDOFF](HANDOFF.md).

## תוספת: העמקה, טעם וביקורת לפני השימוש

בהמשך לאישור שלך נוספה שכבת הנחיות משלימה; התוכן הקודם, הסוכנים והכלים נשמרים.
המחקר הנוסף בחן סעיפים נבחרים מתוך Impeccable, Taste Skill, UI UX Pro Max והסקילים של
Emil Kowalski, לצד מקורות כתובים של Valve ו־Riot. אלה שכתובים נבחרים ל־3D, לא עוד ארבע
חבילות שצריך להתקין. חמשת רכיבי העיצוב הקודמים נשארו במקומם.

התוספת מחייבת החלטת עיצוב קצרה ורפרנס חזותי פתוח גם למודל בודד בקבלה ברמת standard/premium,
בדיקת צורה לפני ליטוש, וביקורת חזותית ראשונית לפני פירוש המדדים. המלצות low-poly, תאורה,
שחיקה ואקראיות נבחנות לפי הפרויקט; הן אינן הגדרה אוטומטית לטעם טוב. תנועה נבדקת לפי
מטרה, חזרתיות ורציפות, ולא לפי חוקי אנימציית אתר שמועתקים למנוע משחק.

אם אין רפרנס שניתן לפתוח, ההשוואה מסומנת לא מאומתת ואין אישור אמנותי מלא.
תקינות, שליטה בחלקים, התאמה חזותית וטעם נידונים בנפרד; prototype אינו הוכחה לעיצוב מקצועי.
התוספת משפרת את שיטת העבודה, אבל עדיין לא הוכחה על המשחק שלך או בניסוי איכות ב־Claude.

הקובץ שניטען לפי הצורך:
[design-judgment.md](../plugins/game-studio/skills/game-studio/references/design-judgment.md).
המקורות, הבחירות, הרישיונות והגבולות:
[דוח המחקר](research/round2/10-design-judgment-additions.md).
מספרי הבדיקות הקודמים מתייחסים לגרסת הבסיס; בדיקות התוספת מפורטות ב־[VALIDATION](VALIDATION.md).
